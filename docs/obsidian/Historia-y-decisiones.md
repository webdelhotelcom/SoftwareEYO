## Decisiones que conviene recordar (y por qué)

- **Un solo proyecto de Supabase para todos los clientes, nunca uno por cliente.** Motivo: quedarse en el plan gratuito — un proyecto por cliente habría significado costo por cliente, y el mandato explícito del proyecto es "cero servicios pagos sin consultar antes".
- **Nunca `Infinity` ni un número gigante como "sin límite" por default.** Si un límite (alojamientos, usuarios) no está configurado explícitamente para un cliente, el sistema **bloquea** en vez de permitir ilimitado. Decisión de negocio, no solo técnica: un límite mal configurado debe fallar de forma visible, no silenciosamente a favor del cliente.
- **La demo vieja y el sitio comercial original nunca se borran ni se editan de forma destructiva** — quedan como referencia histórica hasta que se decida explícitamente retirarlos. Por eso `LEEME (2).md` se marcó como histórico en vez de borrarlo.
- **No inventar contenido comercial.** Testimonios, videos, cifras — si no existen todavía, se ocultan (con `hidden`, reversible) en vez de rellenarse con algo inventado. Aplicado en la Fase 7 de la corrección de auditoría con la tarjeta de testimonio de Elsa.
- **Rama de respaldo antes de cualquier tanda de cambios riesgosa.** Ver `respaldo-pre-correccion-auditoria-2026-08-02` como ejemplo — convención a repetir para la próxima vez que haga falta.
- **"Terminado" significa probado de punta a punta, con datos reales, no solo código que compila.** Regla explícita del usuario para toda la auditoría, y buena práctica a mantener de acá en adelante: cualquier corrección de seguridad se prueba con un intento real de saltársela, no se asume que la política SQL hace lo que el comentario dice que hace.
- **Redesplegar antes de probar en vivo, siempre que el frontend haya cambiado en la sesión.** Lección aprendida en la Fase 5 de la corrección de auditoría: una prueba en vivo contra el sitio de Netlify sin redeploy previo usa el código VIEJO — produce falsos negativos silenciosos (parece que algo no funciona, cuando en realidad ni siquiera se está probando el código nuevo).
- **Deploy Preview (`draft=true` en la API de Netlify) para cualquier cambio grande de frontend, nunca directo a producción, y nunca pidiendo el token "para probar" como si fuera un paso menor.** Establecido en la Fase 3 después de que el usuario corrigiera explícitamente el hábito de pedir el token de Netlify para deploys de prueba — la corrección: el token solo se pide para un deploy real (draft o producción), aclarando siempre cuál de los dos es. `POST /deploys/{id}/restore` recién publica a producción con aprobación explícita.
- **Los pedidos grandes de este proyecto suelen pasar por varias rondas de correcciones en modo plan antes de aprobarse — cada ronda hay que investigarla contra el código real, no responder desde la memoria de la ronda anterior.** Patrón repetido en Fase 2 y Fase 3: el usuario corrige el plan (a veces varias veces seguidas), cada corrección puede revelar un supuesto equivocado (ej. "sidebar_color debería seguir aplicándose" resultó ser al revés — el usuario lo quería retirado por completo) que solo se resuelve leyendo el código de nuevo, no repitiendo la respuesta anterior con más detalle. El botón de pago de Mercado Pago (2026-09-02/03) confirma que esto sigue vigente incluso para pedidos técnicos hacia afuera del código (correcciones sobre qué API de un tercero usar) — cada ronda se verificó contra documentación oficial real, nunca contra la memoria de la ronda anterior.
- **Nunca confiar en una skill oficial (ni en ninguna otra fuente) para decisiones de arquitectura sin verificar contra documentación vigente primero.** La skill `mp-integrate` de Mercado Pago recomendaba Preferences/Checkout Pro clásico — desactualizado, la documentación real ya trata eso como legacy. Se detectó solo porque se verificó cada corrección del usuario contra la fuente oficial en vez de asumir que la skill tenía razón (o que el usuario la tenía, sin comprobar tampoco).
- **Antes de generar un token de acceso (GitHub, o cualquier servicio con varias cuentas posibles), confirmar en pantalla cuál cuenta está activa.** Se perdieron 2 tokens generados "rápido" antes de confirmar la cuenta logueada en el navegador — el usuario tiene 3 cuentas de GitHub reales, y sin esa confirmación previa es fácil generar un token de la cuenta equivocada.

## Errores propios detectados y corregidos en el camino

Vale la pena dejarlos anotados porque son el tipo de error que se puede repetir:

- El SQL Editor de Supabase corre todo el script pegado como **una sola transacción**: si una sentencia falla, se deshace TODO lo anterior de esa misma ejecución, aunque haya dicho "Success" en un paso intermedio. Pasó más de una vez durante la auditoría.
- Los CTEs (`with x as (...)`) dentro de una misma sentencia `WITH` **no se ven entre sí** (misma snapshot) — un trigger que lee una tabla que otro CTE de la misma sentencia acaba de insertar no la va a ver. Hace falta partir en sentencias separadas cuando hay esa dependencia.
- Un backfill de permisos para tenants nuevos y otro para tenants existentes, escritos a mano por separado, se desalinearon (el rol `propietario` quedó con un permiso distinto según la fecha de alta del tenant) — corregido en `0022`. Lección: cuando la misma regla de negocio se escribe dos veces en dos lugares del código SQL, alto riesgo de que se desalineen con el tiempo; preferible extraerla a una sola función cuando sea posible.
- **El SQL Editor de Supabase corre como postgres/superusuario y se salta RLS siempre**, aunque se simule una sesión con `set_config('request.jwt.claims', ...)` — no sirve para probar aislamiento multi-tenant. Un diagnóstico así, durante la carga de la demo de video (2026-09-01), dio un resultado que parecía confirmar una fuga de datos entre tenants que en realidad no existía. La forma correcta de probar RLS es siempre con una sesión de usuario real (login real en el navegador), nunca desde el editor SQL.
- **Un script que borra filas en orden equivocado puede fallar por una tabla auditada que se repuebla a sí misma.** Pasó dos veces en este proyecto con la misma causa (`reset_tenant_orielesymama.sql` ya lo documentaba, y el script de borrado de la demo de 2026-09-02 lo repitió): borrar `audit_log` antes que una tabla auditada (como `profiles`) no sirve, porque el propio borrado de esa tabla vuelve a insertar filas en `audit_log` vía trigger. Regla fija: `audit_log` siempre al final de cualquier script de borrado, sin excepción.
